Props preserving

By default a DataTable forgets everything the moment it unmounts — the search box empties, the sort resets, the card view flips back to the table. options.props gives you two hooks to change that: set, which hands you the table’s state every time it changes, and get, which the table calls once on mount to ask for it back.

Where that state actually lives is entirely up to you. The table never touches localStorage, the URL, or a server — it just hands you an object and asks for one back. Local storage and URL query params are both a few lines below.

Type definitions: see Props.

The shape

options={{
  props: {
    set: (props, tableTitle) => void,  // required — called on every state change
    get: () => Partial,                // optional — called once, on mount
  },
}}
NameTypeDescription
set(props: TablePropsInterface & { page: number; limit: number }, tableTitle: string) => voidCalled whenever the user sorts, searches, filters, switches view, or pages. The second argument is the table’s title — see One handler for every table. Required if you set options.props at all.
get() => Partial<TablePropsInterface>Called once while the table first renders, to seed its initial state. Takes no arguments (no title). Optional — and nullable, so get: null is fine too.

The state itself:

type TablePropsInterface = {
  query: string;
  sortBy: string;
  direction: -1 | 1;
  displayAs: string;
  filters: TableFilter[];
};

set additionally receives page and limit; get does not restore them — see Pagination is different.

set — saving state

set fires on every interaction that changes table state:

InteractionWhat it sends
Clicking a sortable headersortBy, direction
Running a searchquery, and page: 1 (searching resets to the first page)
Switching to table / card / a custom viewdisplayAs
Applying or clearing filtersfilters, and page: 1 (a changed filter resets to the first page)
Changing the pagepage
Changing the rows-per-pagelimit

It is not called on mount — only in response to a real interaction.

Every call carries the whole state

set never sends you just the delta. Sorting a column sends the current query and view along with the new sort:

// after clicking the "age" header, with a search already applied
{ sortBy: "age", direction: 1, query: "kaoutar", displayAs: "table" }

That means you can persist the payload wholesale without merging it into anything you saved before — for query, sortBy, direction, displayAs and filters.

Note page and limit are the exception: they only appear on the call that changed them. Sorting sends no page key at all, and changing the page sends no limit. So if you write the payload straight into the URL or a storage key, a sort will wipe whatever page the user was on. Merge into what you already have rather than replacing it:

set: (params) => setSaved((prev) => ({ ...prev, ...params }))

get — restoring state

get is called once, while the table renders for the first time, and its return value seeds the initial state. It’s read per-key with a fallback, so a partial object is fine — anything you leave out just gets the default:

KeyDefault when absent
query""
sortBy"" (no column sorted)
direction1 (ascending)
displayAs"table"
filters[] (nothing filtered)

It seeds the initial state and then gets out of the way — it is never consulted again, so it can’t fight the user’s later interactions.

Restoring the sort restores the indicator, not the order

Note This one will bite you if you don’t plan for it. A restored sortBy/direction puts the arrow back on the right column, but nothing re-applies that sort to your rows:

  • On a static table, data is re-read from the prop you passed, so the rows come back in their original order under a header that claims they’re sorted.
  • On a dynamic table, the fetch the table fires on mount sends page, limit and search — but not sortBy or direction — so your API returns unsorted rows.

The restored query does make it into that mount fetch (as search), so search restores end-to-end. It’s specifically sort that needs help from you:

// static: sort the data yourself before handing it over
const saved = read();
const rows = useMemo(() => sortRows(allRows, saved.sortBy, saved.direction), [saved]);
 
// dynamic: include the saved sort in your own initial fetch
useEffect(() => {
  fetchRows({ ...saved, page: saved.page ?? 1 });
}, []);

Pagination is different

Note get must not return page or limit. They aren’t part of TablePropsInterface and the table ignores them there. Pagination is restored through the pagination prop instead:

<DataTable
  pagination={{
    total,
    page: saved.page ?? 1,     // ← restored here
    limit: saved.limit ?? 10,  // ← and here
  }}
  options={{
    props: {
      set: saveSomewhere,
      get: () => ({ query, sortBy, direction, displayAs }), // ← not page/limit
    },
  }}
/>

The asymmetry is deliberate: set reports page and limit so you can persist them, but the table takes them back as ordinary props, the same way it takes total.

Recipe: local storage

Good for “remember how I like this table” — survives reloads and new tabs, scoped to the browser.

Note Use a key that includes the table’s identity ("orders-table", not "table") — two tables sharing one key will overwrite each other’s state. If you’d rather not hard-code one key per table, set hands you the table’s title as its second argument — see One handler for every table.

Recipe: URL query params

Good for “send someone this exact view” — the state lives in the address bar, so the URL is shareable, bookmarkable, and survives the back button.

Opening /orders gives you a clean table. Opening /orders?limit=20&query=search&sortBy=total&direction=-1 gives you the same table already searched for search, sorted by total descending, showing 20 rows a page — because those params are what get and the pagination prop read on the way in.

Two details worth copying from that snippet:

  • Seed the merge from the current URL (new URLSearchParams(params)), not from an empty one. Because a sort sends no page key, replacing the whole query string would silently drop the page the user was on.
  • Delete empty values instead of writing them. Otherwise clearing the search box leaves ?query= hanging around in every link the user copies.

For a dynamic table, the URL and your actions.get are reading the same state from two directions — the table calls actions.get with its own params, and set writes those same values to the URL. They stay in step because both are driven by the same interaction.

One handler for every table

set receives the table’s title as a second argument, so a single shared handler can key its own storage per table instead of you writing one handler per table:

const setTableProps = (props, tableTitle) =>
  localStorage.setItem(tableTitle, JSON.stringify(props));
 
<DataTable title="orders" options={{ props: { set: setTableProps } }} />
<DataTable title="invoices" options={{ props: { set: setTableProps } }} />

Both tables share one function and still write to their own key. The same title arrives on every kind of change — sort, search, view switch, page and limit.

Note get does not receive the title — it takes no arguments at all. To read state back per table you still need a handler that knows which table it belongs to, usually a small factory:

const tableProps = (tableTitle: string) => ({
  set: (props) => localStorage.setItem(tableTitle, JSON.stringify(props)),
  get: () => JSON.parse(localStorage.getItem(tableTitle) || "{}"),
});
 
<DataTable title="orders" options={{ props: tableProps("orders") }} />

Since title is also what the table displays in its header, treat it as a storage key you’re committing to: renaming the table later orphans whatever was saved under the old name.

Current limitations

  • Restoring a sort doesn’t re-sort anything — you get the indicator back, not the order. See above for the workaround on both static and dynamic tables.
  • set is required as soon as you provide options.props; there’s no read-only mode where you restore state without also being handed every change.
  • page and limit are reported by set but not restored by get — they have to round-trip through the pagination prop.
  • The payload’s type says page and limit are always present, but at runtime they only appear on the call that changed them. Treat them as optional.
  • Column visibility (the show/hide menu) isn’t part of the preserved state.
